# Legacy procedure details (version-1 settings)

These rules sat in SKILL.md section 2 ("Fetch and calculate") until release 0.7.21 moved them here, as pipeline-brief's legacy procedure moved at 0.7.0; the wording is unchanged. They apply to settings saved before version 2 only. On the confirmed-profile workflow (SKILL.md section 1, `workflow.py`) every read comes from `workflow.py plan` and `report` prints the result, so nothing here applies there.

## Fetch and calculate (section 2)

Stages come from the account-context read (no stage tool; once per chat session, fresh for each new chat and scheduled run): save that response and pass it to compute with `--stages`. When the user states an as-of date, pass it as `--today <YYYY-MM-DD>` to every script and use it for every "days since" and overdue statement. Read open deals, won/lost deals, and completed activities across the scope on every run, whether or not a risk adjustment is configured: every recency or silence statement in the result rests on that read, and a run without it says activity evidence is incomplete for every deal (0.7.12 phase 2 check). Fetch completed activities in pages, never once per deal: `getActivities` with `done=true`, `limit` 100, `sort_by` `update_time`, `sort_direction` `desc` and `updated_since` 90 days before today, after each page run `run_capture.py absorb --run <run-record-path>`: it saves the next page's parameters to `./.pipedrive-sales/runs/next-page-params.json` and prints them, and the next `getActivities` call uses exactly those parameters, copied from that output, never a cursor from memory or read out of a response file; stop when it prints no further page; at most six activity calls, after which the script itself reports the unread cursor as partial activity coverage (recency unknown for the deals without a loaded activity). The run record is never edited by hand: a page whose cursor was not the saved one is left out by absorb itself (it says so), and any other call to leave out is recorded with `run_capture.py exclude --run <run-record-path> --tool-use-id <id> --reason <why>`. (0.7.11 run (c): one `done=true` read of 500 rows came back as a host file pointer, not data; the plugin hook now saves such a file itself, and `run_capture.py absorb` adds it to the run.) Save the run record at `./.pipedrive-sales/runs/<date>-forecast.json` as one JSON object: `{ "today": "YYYY-MM-DD", "calls": [{ "tool": "getDeals", "params": { ... }, "response": <exact MCP response> }] }`. Copy each MCP response verbatim and retain connector parameter arrays such as `"status":["open"]` unchanged. For a tool error without a response, keep the exact error text in that call's `error` field with `response: null`; never turn the error into an invented successful response. Run `scripts/compute.py --config ./.pipedrive-sales/config.json --input <run-record-path> --stages <saved context response> --period <YYYY-MM | YYYY-Qn | YYYY-MM-DD> --today <date> --markdown --output ./.pipedrive-sales/results/forecast-full.json --lens '{"type":"owner_pipeline","id":"<owner-id>:<pipeline-id>"}'` for a confirmed owner-within-pipeline request; use the corresponding JSON object for an owner or pipeline lens, and omit `--lens` only for a confirmed team-wide run. Verify the printed `Scope:` line and matching target before presenting figures. `--markdown` prints the ready-to-paste text and `--output` makes the script write the complete result to `./.pipedrive-sales/results/forecast-full.json` itself; never redirect script output to a file yourself, and never run the command bare for the paste (a bare run prints the full JSON, which the client saves to a file you cannot read). Complete inline connector JSON may be copied unchanged and checked using `response_capture.py --inline-json` in `references/response-capture.md`. An inaccessible transcript or missing original wire bytes does not block this route. Stop only if a response is incomplete or cannot be retained and checked accurately. Never infer or reconstruct missing deal rows. Do not create sample-data helper scripts. Do not inspect unrelated skill files, `compute.py`, or `pdcore.py`, and do not enumerate the workspace before the required reads. The compute result is the sole source for every number, dashboard, history entry, and triage handoff.

Core stage or open-deal evidence that is failed, malformed, or incomplete stops the forecast. Explain the evidence problem and offer a self-contained pasted-list/CSV fallback; never mix pasted and CRM rows. A 403 on the context read is such a failure: say the reconnect line from "Connector errors, missing tools and tool names" in `references/account-context-guide.md` first, then make the pasted-list offer, and show no numbers. A failed or partial activity read does not stop the forecast: use the pages you have and say which haircuts and deals are unavailable, so the adjusted forecast may be optimistic.

Probability precedence is deal probability, varying CRM stage probability, accepted local ladder, then unweighted. If all CRM stages are 100% and no deal probability exists, the result is unweighted and `compute.py --markdown` prints the stage-ladder offer (“Use these, edit them, or leave it unweighted.”) after the Markdown: paste it with the rest and do not write or drop it yourself. The ladder is never written to Pipedrive and never overrides a CRM value.
If stage probabilities are out of order, name the affected stages and calculate the
current forecast impact only from included deals whose `probability_source` is `stage`.
If none use that stage default, say its current impact is zero; do not call it small. For a pipeline named in the result's `stage_order_notices` (no Pipedrive `order_nr`), make no out-of-order claim; the script prints no ladder offer; the stage breakdown keeps the order Pipedrive returned.

Show active risk adjustment settings in a short assumptions line after each interactive result. If the saved config has no `forecast.haircuts`, show the unadjusted result as such and explain that silence, no-next-step, and slipped-date risk has not reduced the number. After the result, offer “Review how inactive deals affect this estimate?” Show the starter multipliers only when the user wants that review, and apply them only after explicit acceptance. Do not say there are no at-risk deals solely because adjustments are inactive. On an edit, restate the proposed values and require explicit confirmation before writing local configuration. Recompute from the already fetched result; make no additional Pipedrive call.
